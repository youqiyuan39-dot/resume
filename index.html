Agent Harness

模型外面那一层：决定它能看什么、能做什么、什么时候必须停

模型负责理解问题、选工具、写候选；Harness 负责其余的一切。悠悠的工作台助手基于 AgentScope 的 ReAct 循环，外面这几层约束是我按业务风险定义、逐条验收的。

  • 7 / 8ReAct 最多 7 轮推理一次问答最多 8 次工具调用
  • 16逐个 SKU 处理时最多 16 次模型请求同时限 240 秒、4.8 万 token；整件商品的阶段另设上限
  • 预览写工具只生成待确认预览运营确认后才执行，发布走独立的发布中心
  1. 工具注册关联商品时只开放 5 个读工具和 3 个只生成预览的写工具worker.py
  2. 证据优先首轮强制调用读取工具（tool_choice = required），不能空口回答当前状态worker.py
  3. 范围绑定工具参数里的商品被强制为当前商品，越界直接报错worker.py
  4. 预算与停止到达轮次、调用、时间或 token 上限就停，保留已通过的步骤，标明未完成task_control_v3.py
  5. 输出校验结构化输出不合 schema 时，把出错字段路径反馈给模型重试一次；同样的错再出现就停task_control_v3.py
  6. 回答校验回答漏掉条码、重量、尺寸等关键缺项时，程序改为直接列出核对记录worker.py
  7. 执行轨迹每个 SKU 一份 JSONL 轨迹：请求摘要、用量、结果，密钥脱敏后落盘task_control_v3.py

另一个模块“核查 Agent”同理：最多 6 轮、12 次工具调用，重复调用会被识别，结果只是候选、不允许发布（product_audit_agent.py）。

Harness 实例：一次工具调用

模型到底在哪里做决定？

运营在工作台关联一件商品后问助手：“这件商品为什么不能发布？”下面是这一问在代码里的完整路径。黄色步骤由模型决定，蓝色步骤由代码强制约束。

  • 模型决定选哪个工具、怎么解释、提出什么修改
  • 代码约束绑定商品、预取证据、校验回答、限制写入

上限：ReAct 最多 7 轮，工具调用最多 8 次；查询失败返回“本次未取得，不可推测”。

源码：src/workbench_assistant_worker.py（AgentScope ReAct）

运营这件商品为什么不能发布？

  1. 代码
    绑定当前商品

    本轮只回答已关联的这一件；工具参数里的商品名被强制为当前商品，换成别的商品直接报错。

    context.product = "节日门帘-draft.json"
  2. 代码
    预取证据

    推理前先查商品状态和最近处理日志，作为模型的上下文。

    inspect_product · get_product_logs
  3. 模型
    选择下一步查询

    首轮必须先调用读取工具，具体调哪个由模型决定：它要看完整缺项。

    inspect_product(detail_level="full")
  4. 模型
    根据工具结果解释缺项

    “缺包装重量和三边尺寸，条码豁免依据未取得，所以还不能发布。”

  5. 代码
    校验回答

    回答漏掉条码、重量、尺寸等关键缺项，或把内部工具名写进回答时，程序改为直接列出核对记录。

    checked_product_answer()
  6. 模型
    提出修改预览

    运营补充实测重量后，模型调用写工具准备修改。

    prepare_product_change({"packed_weight_g": 420})
  7. 代码
    校验执行条件

    写工具只生成待确认预览：字段限白名单，每轮只能有一个预览；运营确认后才写入，发布走独立的发布中心。

项目知识库 · RAG

模型不懂的业务规则，从知识库里按需取

利润口径、包装事实边界、多 SKU 隔离、型号怎么填，这些规则写在 22 条知识文档里，每条标明类型、来源和更新日期。助手回答前先检索，只把相关的几条连同来源放进上下文。

源码：src/project_knowledge_v3.py · knowledge/project/knowledge.json
  1. 过滤只取状态有效、未过期的用户规则和项目约定
  2. 双路召回BM25（中文双字 + 业务同义词）和 BGE 中文小模型向量（本机 CPU）
  3. 融合RRF 合并两路排名，向量相似度低于 0.52 的不进入
  4. 控长最多 4 条、5000 字，保留来源和版本
  5. 边界规则不能当当前商品事实，实时状态由工具读取；向量服务离线时回退 BM25 并标明

    浏览器里按源码复现的是 BM25 这一路（含同义词扩展），文档是仓库里的真实知识库；线上还会叠加 BGE 向量并用 RRF 融合，排序可能略有不同。

    框架对照

    换成 LangChain / LangGraph，这些机制分别对应什么

    悠悠的 Harness 基于 AgentScope 和自己写的约束，没有使用 LangChain。下面是我对两边概念的对照：如果团队用 LangChain / LangGraph，同样的设计应该落在哪里。

    悠悠里的做法LangChain / LangGraph 中的对应
    AgentScope ReAct，最多 7 轮create_react_agent，用 recursion_limit 限制步数
    带类型参数的读工具和预览写工具@tool / StructuredTool，参数用 Pydantic 定义
    首轮强制先调用读取工具bind_tools(..., tool_choice=...)
    BM25 + BGE 向量，RRF 融合EnsembleRetriever（BM25Retriever + 向量检索器，按 RRF 合并）
    写操作只生成预览，人确认后执行LangGraph 的 interrupt 人工确认节点
    六阶段状态机，原子落盘、断点续跑LangGraph StateGraph + checkpointer
    每个 SKU 的 JSONL 执行轨迹Callbacks / LangSmith tracing

    流程设计

    把上架做成一台不会乱发的状态机

    上架最怕两件事：模型判错还照样发出去，网络超时后重复刊登。悠悠把流程拆成证据、处理、校验、冻结、发布、回查六个串行阶段，任何一步不确定就停下隔离。

    源码：src/autonomous_flow_v3.py
    1. 先落盘，再发布调平台接口前，先把任务写成 dispatching 并原子保存；进程中断后从原阶段续跑。
    2. 结果未知，只回查不重发发布时出任何异常都记为 unknown，转去回读平台，从设计上避免重复刊登。
    3. 以平台回执为完成标准拿到真实 item_id 且确认在线才算完成，否则隔离并写明原因，交给人处理。
